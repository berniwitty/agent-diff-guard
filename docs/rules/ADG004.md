# ADG004 — expected-value-edited

**Default severity:** warn

## What it detects
In a test function present at base and head, an assertion keeps the same *actual*
expression but its *expected* literal changed, **and** a function called in that actual
expression was modified in a non-test file in the same diff.

The expected side is the side of a comparison (`assert a == b`, `assertEqual(a, b)` and
other two-argument comparison methods) that is a literal: a constant, a negated number,
or a tuple/list/set/dict of literals. The other side is the actual expression.

A function counts as modified when its source differs between base and head, or it is
new. Calls are matched by simple name (`calc.add(…)` matches a modified `add`).

## Why it matters
When an implementation changes and a test starts failing, editing the expected value
to match the new output makes the failure disappear without asking whether the new
output is right. Sometimes the old expectation really was wrong; this rule only asks a
reviewer to confirm which.

## Example — flagged
```python
# src/calc.py: add() was changed in this diff
# before
def test_add():
    assert add(2, 3) == 5

# after
def test_add():
    assert add(2, 3) == 6
```

## Example — not flagged
```python
# The expectation changed, but nothing that add() depends on was touched in this
# diff: a test fix on its own.
# before
def test_add():
    assert add(2, 2) == 5

# after
def test_add():
    assert add(2, 2) == 4
```

## Scope and known false positives
- A deliberate behaviour change with updated expectations is flagged; that is the point
  of a `warn` rule. Say why with `# adg: allow ADG004 reason="..."`.
- Matching by simple name can link an assertion to an unrelated function with the same
  name in another module.
- Changes inside helpers the actual expression calls indirectly are not linked.
- Files that fail to parse at base or head are not analysed.
